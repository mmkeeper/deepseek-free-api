# Локальный прокси к DeepSeek (127.0.0.1:18632)

OpenAI-совместимый прокси к chat.deepseek.com. Модели: `dsf-deepseek-flash`
(текст), `dsf-deepseek-chat`, `dsf-deepseek-reasoner`, `dsf-deepseek-vision`
(формулы, страницы PDF). Ключ — любой (`ds-dummy`).

## Главное: ретраи делает ПРОКСИ, а не клиент

При ошибке от DeepSeek прокси САМ повторяет запрос с паузами
**1, 2, 4, 8, 16, 32, 64, 128, 256, 512, 1024 с** — суммарно ~34 минуты.
Этого обычно хватает, чтобы переждать бан DeepSeek («слишком частые сообщения»).

Пока прокси пережидает, он **молчит**: клиент видит не ответ, а тишину.
Связь с локальным прокси рвать нельзя — если бан спадёт, ответ придёт.

### Что из этого следует для клиента

1. **HTTP timeout ≥ 35 минут (2100 с).** Меньший таймаут обрывает ожидание
   на середине цикла: клиент решает «прокси не отвечает», хотя тот ещё
   пережидает. Короткие таймауты (15-300 с) дают ложные `busy` и обрывы.
2. **Свои ретраи не нужны.** Прокси уже сделал 11 попыток. Повторный
   запрос клиента начинает НОВЫЙ 34-минутный цикл, а при активном бане
   продлевает блокировку (подтверждено анализом логов сервера).
3. **Ошибка, пришедшая через ~35 минут, означает: бан не спадёт.** Только
   тогда останавливать прогон. Прогресс держать в почанковом кэше.

## Темп запросов

Бан наступает не от всплеска, а от **устойчивого темпа**: ~3.3 запроса/мин
в течение ~30 минут → блокировка на ~34 минуты. Держать темп ниже:
пауза ≥ 20-35 с между отправками.

Диагностические пробы («жив ли провайдер») — это тоже запросы: они жгут
лимит и сбивают текущее ожидание. Проверять состояние по косвенным
признакам (файлы кэша, процессы), а не новыми запросами.

## Однопоточность и system-сообщение

Прокси обрабатывает **один запрос за раз**. Параллельные запросы
бессмысленны — воркеров держать 1.

Отдельное `system`-сообщение может отвергаться мгновенным
`{"error": "busy"}`. Обход: склеивать инструкции с заданием в ОДНО
`user`-сообщение через разделитель.

## Рабочие настройки

- HTTP timeout — 2100 с на любой вызов.
- retries клиента — 0.
- max_workers — 1.
- пауза между отправками — 20-35 с.

## Настройка таймаутов в Hermes (профиль)

Hermes по умолчанию даёт локальному эндпоинту 900 с (`agent.local_stream_stale_timeout`),
а базовый request timeout — 1800 с. Для прокси нужно 2100 с (35 мин) в ТРЁХ местах.

### Ключевая ловушка: имя провайдера

Рантайм зовёт `get_provider_request_timeout(agent.provider, model)`, а `agent.provider`
для сохранённого custom-эндпоинта равно **`custom:<name>`** (например `custom:dsfree`),
а не `      `. Функция читает ТОЛЬКО секцию `providers:` верхнего уровня — записи из
`custom_providers:` (list) она не видит.

Отсюда: таймауты надо класть в `providers['custom:dsfree']`.

### Вторая ловушка: пустая запись ломает маршрут

Если добавить в `providers` запись с ОДНИМИ таймаутами (без `base_url`), она
замаскирует рабочую запись из `custom_providers` — и `resolve_provider_full` вернёт
ПУСТОЙ base_url. Подключение к модели сломается молча.

Запись в `providers` должна быть ПОЛНОЙ: `base_url`, `api_key`, таймауты.

### Рабочая конфигурация

```yaml
providers:
  custom:dsfree:
    base_url: http://127.0.0.1:18632/v1
    api_key: ds-dummy
    request_timeout_seconds: 2100
    stale_timeout_seconds: 2100
agent:
  local_stream_stale_timeout: 2100
```

`hermes config set providers.dsfree...` создаёт ключ `dsfree`, который рантайм
НЕ использует — нужен именно `custom:dsfree` (через `--force`, имя с двоеточием
не в реестре ключей).

### Проверка после правки (обязательно)

```python
from hermes_cli.config import load_config_readonly, get_compatible_custom_providers
from hermes_cli.providers import resolve_provider_full
from hermes_cli.timeouts import get_provider_request_timeout, get_provider_stale_timeout
c = load_config_readonly()
prov, model = c["model"]["provider"], c["model"]["default"]
pdef = resolve_provider_full(prov, c.get("providers"), get_compatible_custom_providers(c))
assert pdef and pdef.base_url, "маршрут сломан!"
assert get_provider_request_timeout(prov, model) == 2100.0
```

## TTS-эндпоинты (озвучка)

**Обязательный конфиг: `max_text_length` для провайдера.** Hermes режет текст на чанки по `tts.<provider>.max_text_length`, а для незнакомого провайдера берёт `FALLBACK_MAX_TEXT_LENGTH = 4000`. Плагин deepseek-session текст игнорирует и каждый вызов возвращает один и тот же ответ сессии — значит N чанков = N запросов = один ответ, озвученный N раз подряд. Симптом: `TTS text for provider ... split into 2 chunks` в agent.log и два файла `.chunk00N.ogg` одинакового размера. Лечение: `hermes config set tts.deepseek-session.max_text_length 1000000` (CLI предупредит 'not a recognized config key' — это нормально, ключ читается динамически). После правки нужен перезапуск: `load_config` кэшируется в `_CONFIG_CACHE`.

**Номер сообщения восстанавливается по тексту, а не берётся из конфига.** Плагин получает от Hermes УЖЕ нормализованный текст (`prepare_spoken_text`: markdown, код-блоки, URL, эмодзи, `<think>`, единицы, переводы строк — всё необратимо). Сравнивать с сырым `content` из снапшота нельзя. Решение: импортировать тот же `tools.tts_text_normalize.prepare_spoken_text` и нормализовать обе стороны ДО НЕПОДВИЖНОЙ ТОЧКИ (см. ниже про неидемпотентность), искать с КОНЦА списка (при дубликатах побеждает свежее), `message_index` = 0-based среди assistant-сообщений (прокси считает ВСЕ assistant, включая пустые с `tool_calls`). Нет совпадения → RuntimeError (тишина + запись в лог), НЕ откат на последний ответ: озвучить чужое сообщение хуже, чем не озвучить. Следствие: `/voice tts` для такого провайдера замолкает насовсем — `tts_tool_speaker` режет ответ по предложениям, фрагмент никогда не равен целому сообщению (плагины в реестр стримеров `tts_streaming._REGISTRY` не попадают).

**Нормализатор НЕ идемпотентен — нормализовать до неподвижной точки.** Hermes прогоняет текст через `prepare_spoken_text` ПЕРЕД вызовом провайдера (`tools/tts_tool.py:431`), поэтому плагин получает уже нормализованный текст. Но второй проход даёт ДРУГУЮ строку: на 240 живых сообщениях расхождение у 55. Причина — схлопывание многоточий и «..»: `skillview(name='..')` → `skillview(name='.')`, `Хотя.. инструкция` → `Хотя. инструкция`. Значит «один проход от сырого содержимого» (так текст лежит в снапшоте) и «один проход от пришедшего текста» — разные ключи, и поиск не находит совпадения при живом снапшоте. Симптом обманчив: «текст не найден ни в одной сессии», хотя сессия на месте и снапшот полон — начинаешь искать дефект в кросс-сессионной логике, а он в строковом сравнении. Лечение: приводить обе стороны к неподвижной точке — гонять `prepare_spoken_text` в цикле до `nxt == current` (медиана 1-2 прохода, длинные ответы до ~10, циклов не наблюдалось; предел 24 прохода с возвратом последнего результата). После фикса находятся 37 из 37 реальных ответов вместо 31 из 37. Кэшировать результат по сырому тексту (словарь с полной очисткой при 512 записях): повторный вызов из кэша ~0 с, без кэша 4 мс на 30 тыс. символов.

Проверять идемпотентность на РЕАЛЬНЫХ текстах сессии, а не на коротких пробах: `67`, `Готово.`, `5 кг` проходят второй проход без изменений и создают ложную уверенность. Брать дампы из `<profile>/sessions/request_dump_*.json` — там лежат настоящие ответы с многоточиями, кодом и сносками.

**Третий слой расхождения: desktop прогоняет текст через СВОЙ очиститель.** Между снапшотом и провайдером текст проходит ДВА разных преобразования. Desktop (`apps/desktop/src/lib/speech-text.ts`, `sanitizeTextForSpeech`, вызывается из `playSpeechText` в `lib/voice-playback.ts:669`) снимает markdown-таблицы ЦЕЛИКОМ, снимает заголовки/эмфазис/код-ограждения, а перевод строки без завершающего знака препинания превращает в `.`; `/api/audio/speak` принимает ТОЛЬКО `{text}` (`api/system.ts:speakText`) — ни `messageId`, ни номера сообщения до провайдера не доходят. Hermes затем нормализует ещё раз (`tools/tts_tool.py:431`). Снапшот же хранит СЫРОЙ markdown. Итог: сравнение «сырое против пришедшего» расходится ровно на ответах с таблицей/заголовком — замер на 3876 живых ответах дал 1691 промах (совпало 2185). Лечение: портировать `sanitizeTextForSpeech` в плагин и применять к текстам снапшота ПЕРЕД стабилизацией; с ним 3877 из 3877. Симптом в логе узнаётся по расхождению одного знака: `закончится. Сейчас` (запрошено) против `закончится, Сейчас` (в снапшоте) — точка против запятой, длина 761 против 1071. Порт валидировать на РЕАЛЬНЫХ промахах из `agent.log`: сопоставлять `len` из строки ПРОМАХ и префикс запрошенного текста с `canon(sanitize(raw))` сообщений из базы.

**Снапшот истории: одного `llm_request` мало.** Этот middleware срабатывает ПЕРЕД отправкой запроса, поэтому последнего ответа ассистента в снапшоте ещё нет — кнопка озвучки у свежего сообщения не находит его и падает. Нужен второй хук `post_llm_call`: он приходит после генерации, и в нём `conversation_history` уже содержит свежий ответ (`_close_transcript_tail` в `agent/turn_finalizer.py` гарантирует инвариант «доставленный final_response ⇒ строка assistant в messages» ДО `_apply_output_hooks`, который и стреляет хуком). Объявлять оба в `plugin.yaml`: `provides_middleware: [llm_request]` и `provides_hooks: [post_llm_call]`. Ловушка: `post_llm_call` передаёт `session_id=agent.session_id`, и он может быть `None` — присваивать `session_id` в снапшот ТОЛЬКО если он непустой, иначе валидный идентификатор затрётся и прокси не найдёт сессию.

**Снапшот хранить ПО СЕССИЯМ, а не одним глобальным списком.** Один `_captured` на процесс — источник кросс-сессионного дефекта: при переключении сессий UI монтирует композер новой сессии, `sessionId` меняется раньше, чем `$messages` (он заменяется через RAF — `use-session-state-cache.ts`), и озвучка уходит с текстом новой сессии, а снапшот ещё держит список старой. Плагин не находил текст, срабатывал fallback `message_index = None` («озвучь самый свежий ответ найденной сессии») — и играл фрагмент ПРЕДЫДУЩЕГО чата. Лечение: `_sessions: Dict[session_id, {"messages", "history", "touched"}]` с вытеснением по LRU (8 сессий), поиск по всем сессиям (сначала точное совпадение по `messages`, затем по `history`), и никакого fallback на «последний ответ»: текст не найден ни в одной сессии → RuntimeError (тишина). Запасной источник `history` нужен именно здесь: свежий ответ в снапшот `llm_request` попасть не может по построению (список уходит ДО генерации), поэтому найденный только в `history` текст означает «эта сессия», а `message_index` не передаётся — прокси озвучит её свежий ответ по ключу сессии. Пустой `session_id` не сохранять вообще (запись безадресна). `session_id` доступен в обоих хуках: `turn_api_request.py` кладёт его в middleware-context, `turn_finalizer.py` — в `post_llm_call` (`_apply_request_chain` прокидывает `**middleware_payload(**kwargs)`). Проверять логику изолированно: загрузить плагин через `importlib.util.spec_from_file_location`, подменить `_load_config` и `urllib.request.urlopen`, проверить кросс-сессионный сценарий (текст из A не должен находиться при живой B).

**Озвучка свежего ответа при по-сессионном хранении.** Если текст не нашёлся нигде, а список сессии заканчивается `user`/`system` — это НЕ повод озвучивать «последний ответ»: такой fallback в старом коде уводил в чужую сессию. Правильно: искать по `history`, и только если и там нет — молчать с ошибкой.

**При переключении сессий на озвучку уходит СКЛЕЙКА нескольких ответов — поиск по равенству её не находит.** Desktop при смене сессии отправляет не одно сообщение, а буфер: в логе `запрошено=...` (len 7878) начинается встык `'Смотрю эту сессию — и в логах, и в базе.Ключевое расхождение: ...'` — это `msg#11521` (40) + `msg#11523` (173) БЕЗ разделителя, между ними лежал tool-вызов. Такого текста нет ни в одном снапшоте как единого сообщения, поэтому `_locate` промахивается всегда, а не иногда. Признак в логе: `len` запрошенного заметно больше любого одиночного ответа (7-8 тыс. против 0.5-2 тыс.), а первые 90 символов совпадают с началом ОДНОГО из ответов, но не с целым. Это тот же кросс-сессионный дефект (вариант A); чинить поиском по вхождению/хвосту НЕ стали — ослабляет защиту «не прочитать чужое». Решение пользователя: оставляем как есть.

**Отсутствие запроса в логе ≠ потеря запроса в прокси.** Если у сообщения в UI видна ошибка озвучки, а в `agent.log` в его окне нет ни `Generating speech`, ни `ПРОМАХ` — запрос НЕ ТЕРЯЛСЯ, его не отправляли: ход закрылся раньше (сравнивать время записи сообщения в `state.db.messages.timestamp` с ближайшим `Turn ended` и стартом нового процесса `run_agent`/`Loaded environment variables`). Ошибка в UI в этом случае принадлежит ДРУГОМУ сообщению (кросс-сессионный дефект: при переключении озвучивается последнее сообщение уходящей сессии, а ошибка рисуется у сообщения в новой). Проверять гипотезу «кэш/прокси не получил запрос» по наличию пары `Generating speech` → (`сессия ..., message_index=...` | `ПРОМАХ`), а не по факту ошибки в UI.

**Диагностика промахов ограничена: плагин пишет только 90 символов запрошенного.** Строка `ПРОМАХ. запрошено=%r (len %d)` обрезает текст, поэтому отличить склейку от одиночного ответа можно по `len` и по первым 90 символам, но полный текст в логе не увидеть. Полный запрос остаётся только в дампе `$TEMP/deepseek_tts_debug.json` (пишется на ошибку прокси, ключи `time/status/detail/payload`); на промахе поиска дамп НЕ пишется. Для сверки брать текст из `state.db.messages` и склеивать кандидатов в Python.

**Две одинаковые записи `TTS audio saved` подряд — НЕ дублирование запроса.** Один лог-вызов приходит из `_text_to_speech_single` (на чанк), второй из `text_to_speech_tool` (на финальный файл). Признак реального дублирования — только `split into N chunks` плюс совпадающие размеры чанков.

Прокси умеет озвучивать ответы DeepSeek — но НЕ произвольный текст.
Контракт и границы: `references/tts-endpoint.md`.
Подключение прокси как TTS-провайдера Hermes: `references/hermes-tts-plugin.md`.

Главное, что определяет все решения: `POST /v1/audio/tts` принимает либо
`chat_session_id` (выданный прокси), либо `messages` в формате chat/completions —
и озвучивает сообщение ИЗ СВОЕЙ истории по номеру. Поля `input`/`text` нет и не
будет (ограничение DeepSeek TTS API). Поэтому сценарий «озвучь вот этот текст»
напрямую не поддержан: нужен либо номер сообщения, либо сверка по содержимому.
