# Архитектура плагина deepseek-session TTS

## 1. Задача

Прокси умеет озвучивать **только свои** ответы DeepSeek — по номеру
сообщения в сессии, которую он сам ведёт. Свободного текста он не принимает.

Hermes же присылает провайдеру **текст**. Значит, между ними нужен слой,
который восстановит: «какой сессии и какому по счёту ответу принадлежит
этот текст».

Этим слоем и является плагин. Он собирает снимки переписок через хуки
Hermes, ищет по ним текст и отправляет прокси **список сообщений найденной
сессии плюс номер ответа**.

```
Hermes                         Плагин                        Прокси
  |                              |                             |
  |-- llm_request -------------->| снапшот messages             |
  |   (перед отправкой в LLM)    |                             |
  |                              |                             |
  |-- post_llm_call ------------>| снапшот history (+ свежий)   |
  |   (после генерации)          |                             |
  |                              |                             |
  |-- synthesize(text) --------->|                             |
  |                              | поиск текста -> (sid, idx)   |
  |                              |                             |
  |                              |-- POST /v1/audio/tts ------->|
  |                              |   {messages, message_index,  |
  |                              |    voice}                    |
  |                              |                             |
  |<--------- ogg opus ----------|<--------- ogg opus ----------|
```

## 2. Два источника снапшотов

Одного хука не хватает — и это неочевидно.

### `llm_request`

Срабатывает **перед** отправкой запроса в модель. В нём есть канонический
список сообщений, который уходит провайдеру. Но **свежего ответа там ещё
нет** по построению: ответ только предстоит сгенерировать.

Следствие: кнопка озвучки у последнего сообщения не нашла бы его в снапшоте
`llm_request` и падала.

### `post_llm_call`

Срабатывает **после** генерации. В нём `conversation_history` уже содержит
свежий ответ. Именно он закрывает дыру.

Ловушка: `post_llm_call` передаёт `session_id`, и он может быть `None`.
Присваивать `session_id` в снапшот **только если он непустой** — иначе
валидный идентификатор затрётся, и прокси не найдёт сессию.

### Раскладка по ключам

| Ключ снапшота | Источник | Что лежит |
|---|---|---|
| `messages` | `llm_request` | канонический список, ушедший в LLM |
| `history` | оба | история после генерации (со свежим ответом) |

## 3. Поиск: три исхода

`_locate(spoken)` возвращает `(session_id, message_index)` или `None`.

| № | Что нашли | `message_index` | Смысл для прокси |
|---|---|---|---|
| 1 | точное совпадение в `messages` | номер | озвучь этот ответ |
| 2 | последняя реплика в `history` | `None` | ответ сгенерирован, но в исходящий список попасть не успел — озвучь **свежий ответ этой сессии** |
| 3 | не нашли (или нашли только в середине истории) | — | озвучивать нечего, ошибка |

Различать исходы 2 и 3 **обязательно**. `message_index=None` — это просьба
«озвучь самый свежий ответ». Если послать её для любой найденной в истории
реплики, старое сообщение озвучится как последний ответ — вместо
запрошенного зазвучит чужой текст.

Не-последняя найденная реплика означает одно из двух, и в обоих случаях
озвучить её нельзя:

* она выпала из канонического списка при **компрессии контекста** (прокси
  считает сессию по отправленному списку — изменившийся список даёт другой
  ключ, и такой реплики прокси не знает);
* это середина переписки, до которой исходящий список вообще не доходит.

## 4. Сравнение текста — три слоя преобразований

Это самая коварная часть. Текст на пути «снапшот → провайдер» проходит
**три разных преобразования**, и сравнивать нужно приведённые значения.

```
снапшот (llm_request)     сырой markdown
        |
        v
desktop                   sanitizeTextForSpeech()   <- снимает таблицы ЦЕЛИКОМ,
                                                        "\n\n" без знака -> "."
        |
        v
Hermes tts_tool.py:431    prepare_spoken_text()
        |
        v
плагин                    _sanitize_for_speech() + _spoken()
```

### Слой 1. Нормализатор Hermes неидемпотентен

Hermes прогоняет текст через `prepare_spoken_text` **перед** вызовом
провайдера. Плагин получает уже нормализованный текст. Но **второй проход
даёт другую строку**: на 240 живых сообщениях расхождение у 55.

Причина — схлопывание многоточий:

```
skillview(name='..')   ->  skillview(name='.')
Хотя.. инструкция      ->  Хотя. инструкция
```

**Лечение:** приводить обе стороны к **неподвижной точке** — гонять
нормализатор в цикле до `nxt == current`. Медиана 1–2 прохода, длинные
ответы до ~10, циклов не наблюдалось; предел `_STABLE_PASSES = 24` с
возвратом последнего результата. Кэш по сырому тексту
(`_SPOKEN_CACHE_MAX = 512`): повторный вызов ~0 с, без кэша 4 мс на 30 тыс.
символов.

### Слой 2. Desktop прогоняет текст через СВОЙ очиститель

Между снапшотом и провайдером текст проходит **два** разных преобразования,
а не одно. Desktop (`apps/desktop/src/lib/speech-text.ts`,
`sanitizeTextForSpeech`) снимает markdown-таблицы целиком, снимает
заголовки/эмфазис/код-ограждения, а перевод строки без завершающего знака
препинания превращает в `.`.

При этом `/api/audio/speak` принимает **только `{text}`** — ни `messageId`,
ни номера сообщения до провайдера не доходят. Единственный ключ — текст.

Снапшот же хранит **сырой markdown**. Итог: сравнение «сырое против
пришедшего» расходится ровно на ответах с таблицей или заголовком.

Замер на **3876 живых ответах**: совпало 2185, промах 1691.

Симптом узнаётся по расхождению одного знака:

```
запрошено:  закончится. Сейчас   (761 симв.)
в снапшоте: закончится, Сейчас   (1071 симв.)
```

**Лечение:** портировать `sanitizeTextForSpeech` в плагин
(`_sanitize_for_speech`, `_strip_md_tables`, `_md_row`) и применять к
текстам снапшота **перед** стабилизацией. С ним **3877 из 3877**.

## 5. Почему снапшоты по сессиям, а не один список

Один общий `_captured` на процесс — источник кросс-сессионного дефекта.

При переключении сессий UI монтирует композер новой сессии: `sessionId`
меняется раньше, чем `$messages` (он заменяется через RAF в
`use-session-state-cache.ts`). Озвучка уходит с текстом новой сессии, а
снапшот ещё держит список старой.

Плагин не находил текст и срабатывал fallback `message_index = None` —
«озвучь самый свежий ответ найденной сессии» — и **играл фрагмент
предыдущего чата**.

**Лечение:** `_sessions: Dict[session_id, {messages, history, touched}]` с
вытеснением по LRU (`_MAX_SESSIONS = 8`), поиск по всем сессиям (сначала
`messages`, затем `history`), и **никакого fallback на «последний ответ»**.

Запасной источник `history` нужен именно здесь: свежий ответ в снапшот
`llm_request` попасть не может по построению, поэтому найденный только в
`history` текст означает «эта сессия», и `message_index` не передаётся —
прокси озвучит её свежий ответ по ключу сессии.

Пустой `session_id` **не сохранять вообще** (запись безадресна).

## 6. Принцип деградации

Не нашли текст → `RuntimeError` → **тишина и запись в лог**.

Никакого отката на «последний ответ»: озвучить чужое сообщение хуже, чем не
озвучить. Прямое следствие: при кросс-сессионном дефекте и склейке ответов
озвучка молчит, а не читает не то.

## 7. Ожидание генерации

Прокси отвечает `503 message_pending`, пока ответ на последний промпт ещё
генерируется. Плагин не озвучивает предшественника, а **повторяет запрос**
до `pending_wait` (45 с), пауза `pending_poll` (0.7 с): то же тело запроса
разрешается в нужный ответ, как только генерация закончится.

## 8. Сохранение аудио

Прокси отдаёт сырой **Ogg Opus**. Плагин определяет контейнер по сигнатуре
(`OggS` / `RIFF` / `fLaC`) и:

* контейнер совпал с расширением цели — пишет файл как есть;
* не совпал — конвертирует через `ffmpeg`, а если его нет, сохраняет с
  правильным расширением рядом.

`ffmpeg` нужен только в ветке несовпадения; обычно не требуется.
